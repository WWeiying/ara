It does not require simulator output to exist to run its unit tests.

**A CVA6 accelerator-interface response is not vector execution-done.** The
scoreboard state `responded` closes only response/ID bookkeeping. Load/store
ownership remains in separate `memory` queues until the respective completion
pulse; it is not removed by a response. Compute responses are not called
execution completions and there is no `ara_idle` or per-functional-unit done
observation in this module harness. `acc_valid_ex_o` is the dispatcher's delayed
issue-acceptance indication, not vector execution completion. "Preserved across
flush" means preservation of the issued request and memory-pending bookkeeping,
not proof of subsequent vector execution.

This interpretation agrees with the inspected sources: CVA6
`core/acc_dispatcher.sv` separately forwards `resp_valid` and counts
`load_complete`/`store_complete`; Ara `hardware/src/ara_dispatcher.sv:1653`
can assert arithmetic `resp_valid` during decode, while lines 5856-5857 forward
separate memory-completion indications. These Ara references clarify semantics;
Ara is not part of the compiled DUT or a source of measured execution coverage.

No full-core or Linux conclusion follows. The external accelerator response
source is a scripted driver; there is no vector execution or memory subsystem.
Completion pulses carry no transaction ID, so this directed schedule associates
each pulse with its oldest still-pending delivered operation of that kind.
The mismatched commit test deliberately challenges a dispatcher boundary with
an ordering not expected from the in-order core. HFENCE observations test the
stall predicate only, not RVH. No nonzero exception, mid-flight reset, unpaired
execute flush, single-commit-port configuration, FPGA FIFO, or store-barrier
`ctrl_halt` contract is claimed. No PULP source or quarantined patch is compiled.
