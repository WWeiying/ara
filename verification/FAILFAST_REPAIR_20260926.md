# 回归调度器退出确认修复

## 实测结论

启动前自测报告的“终止后 PID 仍存在”不能直接认定为进程残留。最小宿主机探针
确认：子进程被 SIGKILL 终止，`wait()` 返回 `-9`，`/proc/<pid>` 已消失，但
`os.kill(pid, 0)` 仍返回成功。对不存在的 PID `2147483646`，该调用也返回成功。
因此，本执行环境下不能把该调用当作存活判据；没有证据表明原失败是 RTL 问题。

原自测仅在最后的 `ProcessLookupError` 断言失败。它前面的断言已经确认发现
失败、保留首错、停止派发待运行任务均生效。之前提出的“回收等待不足”是静态
风险，不应当写成此次失败已证实的根因。

## 修改

- 用 `wait()` 的返回码与 `/proc` 状态检查直接子进程是否已回收。
- SIGKILL 后采用整批统一的有界回收期限，而不是每个进程等 0.1 秒后吞掉超时。
- `STOP.json` 和 `status.json` 记录清理前后状态、信号错误、退出码和回收结果。
- 正在终止的任务先标为 `STOPPING`；确认回收才标 `CANCELLED`。若未确认，
  标为 `TERMINATION_PENDING`，不会把“已发信号”写成“已退出”。
- 另建 session 的后代由独立 systemd 服务的 `KillMode=control-group` 清理。
  直接子进程回收成功不等于所有后代已清理；两层证据分开记录。

## 验证

调度器宿主机单元测试 9/9 通过，包括正常完成、同时成功/失败时不补位、
忽略 SIGTERM 的子进程、回收超时不隐瞒、外部 SIGTERM 和启动失败。

另做一次真实 systemd 故障注入：一个任务另建 session 启动忽略 SIGTERM 的
后代，第二个任务主动返回 7，第三个任务必须不启动。观测结果：

- 状态为 `CANCELLED / FAIL / CANCELLED`，首错返回码保留为 7。
- 直接子进程全部确认回收。
- systemd 服务结束后 `MainPID=0`，ControlGroup 已清空。
- 后代 PID `1173567` 在 `/proc` 中消失，第三个任务没有产生标记文件。

证据目录：`verification/out/failfast-repair-20260926-01/`。
对应服务 `ara-dsa-failfast-selftest-20260926-01.service` 的失败状态是主动注入的
预期结果，不是芯片回归失败。

没有修改 RTL。正式回归仍遵守发现新异常就停止、等待用户指示的规则。
