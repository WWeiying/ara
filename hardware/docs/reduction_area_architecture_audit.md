## 2. VMFPU：分清算术复制与外围状态

源码重点：`lane/vmfpu.sv` 的 `red_exact_sum_eligible`、`i_fpnew_bulk`、`i_fpnew_ordered_fast`、`red_context_*`、`red_stream_*`、`word_red_seed_q`，以及 `lane/fp32_exact_reduction_accum.sv`。

四 Lane 的 +277,310 不是全部由新增加法器产生：短反馈模块当前绝对面积 164,340，精确累加器 72,762；普通 bulk FPU 只增加约 2,508。四种 SIMD 整数乘法器合计反而减少约 12,821，除法器增加约 1,349。VMFPU 本层不含子模块的组合逻辑增加约 30,508、时序单元增加约 18,443。它们与其它小子模块的变化共同构成净差额。不能用 277,310 再加短反馈和累加器面积。

### 2.1 把四套有序短反馈收敛为一套或两套

已实现的固定 ADD、单元素、输出端寄存器配置使独立短反馈模块面积下降 66.626%，但仍然是每 Lane 一套。严格有序求和的一个指令内存在串行累加依赖，因此值得研究把算术资源集中到 RCE 附近：每 Lane 保留源数据 FIFO，中央维护当前指令、逻辑元素位置、累加值、rm 和异常状态，按元素顺序取数；反馈留在中央，不再把每次累加值往返各 Lane。

这需要新的数据供给协议，不能只把三个 Lane 的加法器删除。第一拍源数据、FIFO 跨 Lane 取数、Mask 跳过、宽化转换及最后写回都要有标签和 credit。建议在两个组织中比较：单个共享标量多格式加法器；两组 Lane 各共享一套加法器。后者可能减小连线，但严格有序 token 跨组时仍有代价。现有 RCE 加法器固定 FP64、两级 AFTER；不是可以原样替代所有格式短反馈的一套单元。

必要的容量条件是共享单元的服务率覆盖所有在途有序上下文的合计需求；“一条指令串行”不能证明“多条在途指令只有一份计算需求”。若中央取数造成空泡或与 FP64 收尾争用，需要独立输入队列、仲裁或保留第二个单元。

粗略资源预算：把 164,340 乘以局部剩余比例，约为 54,850；四套变一套最多移除其中三套，毛节省约 41,100，即历史 Ara 基准约 4.5 个百分点。此数尚未扣除集中取数、队列、格式支持和时序修复成本，也不是集成后的面积预测，更不能重复计算上一轮已省掉的部分。

### 2.2 重组精确累加器的更新网络

分段模式保存 16×49 bit 的有符号 bin，每拍接受一个 64-bit word（两项 FP32 或四项 FP16）。目前存在 `segment_bin_d[element_segment] += ...` 的动态选择，并在一个组合循环中按元素依次更新。应检查网表是否形成较宽的读选择、加法和写回选择级联。源码中的动态数组访问只是可疑点，不能直接断言它对应多少门。

优先候选是先统一解码每个元素的段号、带符号贡献、有效位和特殊值，再处理同拍碰撞。比较两种实现：保留少量共享加法器、显式处理相同段的旁路；或按固定 bin 接收解码后的贡献，对同段项先合并，再更新一次 bin。第二种可能把少量加法器变成十六组运算，所以不应未经综合就全量采用。两种都必须保持每拍输入容量，不能以 FP16 四项串行四拍来换面积。

另一条更激进路线是改变精确状态表示：较紧凑的宽整数状态配合分块进位，或局部缓存活跃指数窗口。前者可能减少状态但增加宽移位器与进位控制；后者必须有极端指数分散和抵消时的精确回退，不能只在“指数相近”的输入上正确。它们要作为替代实现与当前方案比较，不是往现有分段累加器上再叠一套硬件。

位宽按最大合法 VL、LMUL、Lane 分配、SEW、宽化和 seed 参与次数推导，有机会减少保守余量，但不会单靠减一两位得到大幅整机收益。尤其现实现借 bin 的高位保存归一化进位和 288-bit 输出，存在 `[48:16]`、`[47:16]` 等固定切片，不能只把 `SegmentBinWidth` 改小。全局状态的范围也不能用单 Lane 元素数推导。

### 2.3 减少同一指令的重复存储

VMFPU 同时保留指令队列、issue/processing 状态、局部上下文、结果队列和按 ID 的特殊值/seed 状态。应先画字段生命周期表，标出哪些字段不可变、哪些是 Lane 私有进度、哪些要活到 VRF grant。候选是每个 VFU 一份小型指令描述表，队列只保存槽号和必要的进度；描述表只存一次 op、SEW、rm、vd、版本和 seed 绑定信息。

建议先在 Lane 内进行，不直接把所有 Lane 元数据集中到一个全芯片多端口表。后者可能用长连线和多端口 mux 抵消寄存器收益。槽号必须与代际/生命周期管理绑定，最后一个结果或 seed 消费者离开后才能复用；local_done 只释放计算资源。不要直接删除正确性修复使用的 `word_red_seed_q`：它承担全 Mask 与 NaN 等语义。Lane 0 独有数据是否已经因常量 lane_id 被裁剪，要查网表，不能把源码数组位数当作四倍实际面积。

## 3. operand_requester：缩小转发范围，而不是删版本检查

源码重点：`lane/operand_requester.sv` 的 `p_forwarded_operands`、`p_recent_mfpu_result`、`p_reduction_result_cache`、`required_forward_be` 和 REQUESTING 分支；`ara_pkg.sv` 定义 9 个 operand queues。

该模块本层组合逻辑差额约 +18,428，时序单元约 +21,043。多个请求端分别保存状态和转发 payload，匹配当前/近期 MFPU、SLDU、两项规约缓存，检查地址、版本与字节覆盖。这说明只缩小两项缓存不足以解释或解决整个 +41,308。

第一候选是按消费者功能拆转发网络：完整向量数据前递保留给需要它的源流；标量规约 seed 通过 RCE 的 seed 路径绑定；其它请求端走 VRF。必须统计每种 requester 的实际命中，以及取消该路径后增加的 VRF 端口冲突。Store、MaskB 等也可能消费规约结果，不能看到“不是 ALU/FPU”就当死逻辑删除。

第二候选是把同一个请求的可复用比较、字节覆盖和来源编码只算一次，再选择数据。可以把 32-bit `forward_bytes/forward_byte_end` 改成经过证明的有界值表达，但综合器可能已经消去高位，不能预报收益。寄存器与数据 mux 的收益比源码变量类型更重要。

第三候选是把规约标量的暂存与 RCE/SLDU seed 表统一。它只适用于相同生产者版本和相同数据范围；普通 VFMUL 全向量结果不能塞进一个标量 seed 表替代。需要维持同拍多个读者和多个写入来源的能力，避免用一个单端口小表让原本并行的请求串行。

## 4. VALU、Lane 调度及中央调度：控制的面积值得单独优化

VALU 本层组合/时序差额约 +11,267/+14,588。源码保留前后台规约 accumulator、三项 local-root 队列（`VInsnQueueDepth-1`）、普通 result queue，以及 RCE pending 状态。当前全配置普通 ALU/FPU 结果队列为 4 项，源码关闭 RCE 时对应默认 2 项。

优先检查在 RCE 已覆盖的操作上，旧 SLDU-tree 后台队列是否仍有可达使用者。如果这些操作总是交给 RCE，可以通过静态 profile 特化去掉只服务旧树的状态与选择；但必须列出完整路由矩阵，检查 VL=0、Mask、不同 Lane 数、未支持格式和宽化等回退。不能看到两条路径共存便认定完全冗余。

另一候选是共享结果存储池，普通向量结果和本地规约根用 owner tag 区分，而保留独立 credit 与提交顺序。共享池可能节省重复 payload，也可能使某类结果堵住全部空间。先做占用分布、同拍读写需求与长期背压测试，再考虑 4→3/2 项；只看平均占用不足以保障吞吐和无死锁。

lane_sequencer 的 +12,529 中，本层时序差额约 +11,300，组合仅约 +522。相对 `30c6971b` 的变化包含 operand 请求版本字段、late-seed 元数据和 global VL 传播。这里优先查宽结构在请求寄存器/队列中重复保存的问题，不应优先增加复杂调度来省几个周期。

中央 sequencer 的 +8,079 对应代码中的寄存器版本、writer 元数据、late-seed 与混合执行的相关性/credit 逻辑等候选来源。可以按发射时生成紧凑描述、消费者保存描述索引的方式合并重复信息；不能减少版本位数而不证明 wraparound、缓存寿命和在途 ID 复用安全。源代码差异提供候选因果关系，精确成本仍需分机制消融。

## 5. RCE 与 SLDU：统一 seed 管理，确认旧精确路径裁剪

RCE 当前 36,522 已包含最终舍入器约 12,951、FP64 加法约 6,679。它已经使用两个上下文和共享合并运算；FP64 为固定 ADD，并非完整通用 FPU。因此“给 RCE 换成加法器”不是新优化点。

SLDU 的 +14,225 需要结合 sparse packet、描述队列、seed 缓存和独立收尾协议看。代码中 SLDU 持有按 ID 的 32-bit 精确 seed/result 表及消费者快照，RCE 还持有通用 64-bit seed 表，operand_requester 有近期结果/规约缓存。建议研究把中央两套 seed 发布/查询合并为一份 64-bit 表，带 producer、vd、version、byte-valid 和 lifetime，word/exact 消费者保存自己的已绑定快照。明确一拍多个写源的优先级或独立写端口；不能把任何值存入后便提前宣布 producer 完成。

合并表未必一定省：两套独立表的读端口若合并成高端口数 mux，可能更贵。先抽取表与匹配逻辑的局部综合比较，检查查询并发，不以表条目数单独判断收益。

已经排除两类“纸面收益”：`EmitRoundedResult=0` 已裁掉不需要的 Lane-local rounder；SLDU 的 `gen_legacy_exact_finalize` 只在 `!RceExactEnable` 时实例化，不能声称当前仍同时存在两套中央 finalizer。其它旧 exact merger 状态也要检查综合网表是否仍存活，不能按 RTL 声明直接计面积。shared extraction 的结果尚待完成；共享首拍更新已实测变大 6.30%，保持关闭。

## 6. 其余差额：不强行归因于规约

MASKU、VLSU、dispatcher、VRF、operand queues 和连接逻辑也有差额。相对固定源码基线，存在 NaN/Mask/宽化与 `simd_mul` 等修复及接口字段扩展。VRF 的差额仅 281，operand queues 仅 1,234；它们不应作为第一批大面积目标。VLSU 与 MASKU 的历史面积增长需先排查依赖版本、约束、接口扇出和映射差异，不能通过取消正确性修复来“还原面积”。

监测计数器若无综合可见消费者通常会被消除。删除未连接统计代码、清理未实例化模块可以改善可维护性，但不应作为显著面积收益宣传。审查脚本保留 +5,859 的未单列残差，没有把它硬塞给某个规约功能。

## 7. 推荐方案组合与验证顺序

| 候选 | 目标硬件 | 预期作用 | 必须先验证的风险 |
|---|---|---|---|
| A：Lane 内共享描述信息 + 消费者特化转发 | VMFPU/VALU/requester/lane_sequencer 的寄存器与 mux | 保留现有算术吞吐，减少外围重复成本；优先 | 端口并发、ID 生命周期、字段最后使用时间、VRF 冲突 |
| B：重组精确 bin 更新 | 四个精确累加器 | 有机会同时降低动态选择网络和组合深度 | 同拍同 bin 碰撞、正负抵消、四项 FP16、首拍与 seed、背压 |
| C：一套或两套共享 ordered backend | 四个已精简的短反馈加法器及 token 路由 | 最明确的进一步算术复制削减方向 | 源供给率、跨 Lane 顺序、多指令吞吐、与 RCE FP64 争用、Fmax |
| D：统一中央 seed 表与静态旧路径特化 | SLDU/RCE 表、旧树控制/队列 | 减少重复 seed 存储和不再使用的控制 | 多写源、已提交生产者、消费者快照、所有回退场景 |
| E：替换精确累加算法 | 整个 unordered 局部 backend | 若 A～D 不够，再改变状态表示 | 数值契约、极端指数、吞吐及关键路径；不可只测常见数据 |

A、B 先用独立开关或替代模块实现，不改变对外时序的候选先做逐周期等价。C 先用请求/服务率与源 FIFO occupancy 记录证明共享资源足够，再改 RTL；不必一开始复制大网络。D 在路由可达性明确后逐项特化。不同方案存在重叠节省和新增端口成本，不把它们的毛收益相加当作总收益。

对每项机制保留相同 ELF 和测量窗口，覆盖独立规约、seed 链、规约/普通同 VFU 混合、Load/Store/Slide/Mask、真实 RAW/WAR/WAW、短 VL、极端 FP、ID 回绕与长背压。A/C/D 要补原 22 项回归之外的多请求端同拍访问、seed 多写源冲突、描述槽耗尽、队列极限压力。记录每类队列高水位、满队列停顿、共享单元冲突、算术忙周期和启动间隔，不能只给平均周期。

公平 PPA 建议分两层：首先在当前冻结源码中比较 `full_compact` 与 A/B/C/D，保持外围、库、工具、约束和 ELF 不变；其次建立固定 `30c6971b` 的优化前实现对照，明确移植的共同正确性/工具兼容修复、依赖快照及其影响。若要单独报告 RCE 论文的增量，则另用已含前期规约优化的 profile baseline，并对两侧应用相同短反馈专用化策略。三种比较分别命名，不能混用。

本轮低风险精简的整机收益未出，因此不为 A～E给出未经验证的最终面积百分比。允许架构变化后，“最多再省 1%～3%”不应当作上限；但要从历史估算约 +35% 到 +5%，需要消除约 30 个基线面积百分点，单靠一个中央 RCE 或 finalizer 显然不够。应优先把复制算术、重复状态和转发网络三类成本同时纳入预算，并根据每项实测结果决定是否进入下一轮实现。
