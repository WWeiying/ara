# 完整模型的投影工作量与后续硬件选择

## 1. 为什么需要这份账目

QKV 的 RTL 配对能证明一个真实调用组是否提速，但不能单独决定整个模型的
优化重点。特别是当前 `WideMatrixDot` 只改变 256 元素 profile 的 M3/M4 局部
wave，不改变 Decode 常见的 M1。不能用 Prefill 切片的收益覆盖 Decode，也不能
因为点积单元更快就认为权重供给和运行时开销已经解决。

本轮工具 `verification/performance/end_to_end_baseline/projection_work_ledger.py`
重新读取已完成的 Qwen3-1.7B Q4_K_M 完整模型配对日志，核对逻辑调用与 native
命令的有效乘积数守恒，并重放原数值与路由检查。此处没有重新运行模型或 RTL，
也没有从 QEMU 的时间推算硬件周期。

## 2. 证据范围

原记录位于验证树的 `verification/out/register-pv-final-models-20261028-01/qwen3/`。
每种 Attention 选择各执行两种 KV 配置；每种配置包含 40-token Prefill 与两次
单 token Decode。下表按一种 Attention 选择合计，因此 Prefill 是两次 40-token
prompt，Decode 是四次单 token 步骤，不是四个独立模型。两种选择的投影调用、
命令形状和工作量相同。

重新检查的内容包括：

- 原有 6 次配对比较、911616 个 logits 的检查结果及 Attention 路由判定。
- 每个模型步骤内，逻辑 `M*N*K` 与全部 native 命令 `m*n*k_blocks*256` 一致。
- native 命令序号、graph epoch、非模拟执行与未分段条件。
- 10 份实际运行产物的原始哈希，包括静态库、ELF、QEMU、启动包和模型盘。
- 收集器及输入文件在处理前后的身份一致性。

本轮不声称旧源码树的全部可变路径已重新通过核验，也不把旧模型记录改标为
当前 RTL 测试。历史产物同时存在以软链接原名记录的 pin，校验必须按原键或
已记录的规范路径找到哈希；如果两个键都存在，两者都须匹配实际字节。

正式回执：`verification/out/e2e_projection_work_ledger_20261106_03/result.json`，
状态 `HISTORICAL_QWEN3_PROJECTION_WORK_REPLAY_PASS`。第一份收集失败保留；
第二份不用于最终依据，正式回执使用冻结收集器重新执行。

## 4. Decode 的主要投影不只有 QKV

Qwen3-1.7B 的 H=2048、F=6144、28 层，词表大小为 151936。按实际逻辑调用的
K/N/profile 分组，每个 Decode token 的量化投影有效 MAC 总数为 1720451072。
表中比例仅在这些量化权重投影内部计算，不含 QK/PV、Softmax、Norm 或其他
算子的成本。

| 投影类别 | MAC 比例 | 逻辑权重字节比例 |
| --- | ---: | ---: |
| Attention 的 Q/K/V/Wo 投影 | 20.4784% | 18.6882% |
| FFN 的 gate/up/down | 61.4353% | 58.1273% |
| 词表输出投影 | 18.0862% | 23.1845% |

逻辑权重字节按原生 profile 的块字节数求和；它不是实测 DDR 流量，不能忽略
缓存、突发对齐或其他访存后直接用于带宽结论。不过，它足以说明后续应优先
补齐 FFN 的长 K 和词表大 N 测量，而不是只反复优化 QKV 的小 N 切片。

## 5. 为什么 Decode 不宜先继续堆乘法器

当前 QBS reader 的数据接口为 128 bit，即理想情况下每周期最多传送 16 字节。
源码 `qbs_engine.sv` 也显式断言这个接口宽度。现有窄 dot 通路每周期最多完成
32 个 INT8 乘积；M1 没有多输入行带来的权重复用。

- Q4_K：每 256 个权重占 144 字节，满速 dot 需要 `32*144/256=18 B/cycle`。
- Q6_K：每 256 个权重占 210 字节，满速 dot 需要 `32*210/256=26.25 B/cycle`。

对 M1/N32/K2048，得到以下服务需求：

| profile | 权重 payload | 理想 R beat 下界 | 原 dot issue 预算 | 当前候选 dot 预算 |
| --- | ---: | ---: | ---: | ---: |
| Q4_K | 36864 B | 2304 cycles | 2048 cycles | 2048 cycles |
| Q6_K | 53760 B | 3360 cycles | 2048 cycles | 2048 cycles |

R beat 下界只包含权重，不含 descriptor、激活、对齐浪费、地址及响应间隙。
dot issue 预算也不包含 FP 修正、流水首尾、依赖及软件开销。这些不是两组实测
时间，更不能相加作为 stall breakdown。

它说明在当前接口下，仅提高 M1 dot 吞吐不会降低权重传输的服务下界；但并不
证明实际 reader 已经满带宽。真实收益还要检查 R 有效传输、无在途请求、等待
响应、接收反压及命令间空隙。能够减少这些空隙或控制成本的适度缓冲、请求
组织和运行时改动，仍可能有很高收益。

M4 则不同：同一权重为四个输入行服务，Q4_K 的 64 乘积/cycle 候选需要约
9 B/cycle 的权重供给，Q6_K 约 13.125 B/cycle。加上激活和其他流量后仍须实测，
但它解释了为什么同一硬件中 Prefill 与 Decode 应采用不同的优化优先级。

## 6. 对下一阶段方案的影响

1. **Prefill：**完成全 N QKV 后，补真实 FFN gate/up/down 的长 K 点，核查更快
   的 dot 是否仍由数据供给、修正和 FP 累积有效支撑。保留完整调用的准备成本。
2. **Decode：**先测 M1 的权重供给效率及 SDK/命令成本。优先比较减少请求空隙、
   命令与配置重复、激活准备和部分和搬运的方案，不预设必须扩大算术阵列。
3. **Attention：**继续实际 GQA/可见历史下的完整调用配对，包含 Softmax/PV，
   不把量化投影工作量当成 Attention 的总占比。
4. **整模型：**用当前运行时的复用记录和代表性 RTL 周期校准账目。未测区域
   保留未知，不把历史调用次数、MAC 比例或服务下界伪装成已测端到端加速。

必要的新 SRAM、队列或算术资源并不排除；选择依据仍是可消除的真实周期与
资源投入，而非“必须复用”或“必须只改 QBS/AKV”。本阶段仍不启动综合。
