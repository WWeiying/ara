## 3. 最新端到端证据修正了哪些认识

### 3.1 同一硬件上的软件开销确实值得优先处理

四个 Qwen3-1.7B Q4_K_M、F16 KV 完整应用使用同一位流和单 worker。
baseline 为修复后的生产软件；candidate 为 trace 查询外提的软件候选，并显式开启
M4 prepare/packed/parallel sums/cache 等组合。不能把它当成纯硬件加速比。

| 阶段 | baseline 合计秒 | candidate 合计秒 | 合计时间比 |
| --- | ---: | ---: | ---: |
| Prefill | 4558.76303 | 3310.94867 | 1.3769x |
| Decode | 2647.16506 | 2141.96137 | 1.2359x |
| 应用 inference 区间 | 7246.14 | 5522.84 | 1.3120x |
| 宿主端完整经过时间 | 9813.058918 | 8140.827426 | 1.2054x |

四项 prompt/generated 长度分别为 135/41、212/70、676/33、174/94。
配对回答和 native 工作计数一致；只有第一项具有 baseline 全 logits 的完整比较，
不能把其余三项写为每个 logit 均已比较。每项每配置是一轮完整运行，另有配对诊断。

candidate 的应用 inference 区间中，Prefill 占约 59.95%，Decode 占 38.78%，
剩余约 1.27%。这只是这组请求的阶段分布，不是 QBS、AKV、Norm 的模块分布。
宿主端时间还包含装载、传输和编排，不能拿它直接预测稳态 token/s。

**结论：下一轮不能仍以 10 月旧 SDK 作为唯一性能基线，否则会把已经找到的
软件开销再次算成硬件优化机会。** 候选源码与部署身份需审查固化，而不是直接覆盖
当前生产 ELF。

### 3.2 M4 并非 Decode 的普遍提速开关

独立 ABBA 对照的 M4 组合收益为：Prefill 1.1575x、Decode 0.9957x、
应用 inference 1.0686x。Decode 没有改善，不能删除该负结果。

应把 M4 的重点放在多行输入的 Prefill，并核对生产命令是否真的启用它。
原始应用命令没有开启四个 M4 opt-in 开关；仅确认编译了相关函数，不等于运行过。

### 3.3 量化 Attention 已有完整回答对照，不必重复证明其可运行

相同 Q4_0 K / Q8_0 V、相同 native QK 数值路径，135-token prompt、
55-token 输出的完整模型配对：

| 阶段 | native 普通调度秒 | grouped Prefill + Register-PV 秒 | 时间比 |
| --- | ---: | ---: | ---: |
| Prefill | 576.43740 | 493.03989 | 1.1691x |
| Decode | 649.71779 | 610.09941 | 1.0649x |
| 应用 inference | 1242.36 | 1119.31 | 1.1099x |

8508416 个 logits 位级一致，完整回答一致，实际优化入口已检查。
两侧投影工作相同；增量来自 Attention 调度，不是从普通 CPU 切到 native QK。
该次完整回答是一组配对；另有六组平衡 warm-prefix 配对，Register-PV 的
Q4/Q8 KV Decode 增量分别约 1.0483x/1.0514x。

这支持继续检查 Attention 的剩余数据搬运，但不意味着新提议的输出驻留已有收益。
F16 KV 的四个应用不会使用量化 Register-PV，因此二者必须保留独立的测试组。

## 4. 数据准备复用已有实证，不能重新包装

历史图探针最终缓存统计为：2208 次查询，1328 次命中，880 次未命中，
880 次准备计算；各图开关前后统计一致。命中率约 60.14%，但这是特定 QEMU
功能测试的缓存行为，不是当前板测的省周期比例。

此外，板测静态适用性报告中，约 92.13% 的 M1 命令属于 context 模式。
这是命令数量比例，不能当作执行时间比例。只适用于 DIRECT 的 lookahead
并不会自动加速这大部分 context 命令。

后续准备优化应回答：剩余 miss 是数据真正不同、容量不足、布局不匹配，还是
重复数据未被复用？不能直接以“命中率未达 100%”决定扩大缓存。

## 6. 收敛后的下一项操作

先固定已测的软件热路径修复与 M4 配置，使它成为后续可重建的候选基线；这一步
不包含自动上线。然后在现有真实 Qwen3 捕获上，用独立实验 helper 实现输出 tile
驻留，原 Register-PV 作为直接对照，不改已封存 helper。

首个判别实验保留 D128、GQA2、原始真实输入和原累积顺序，先核对反汇编是否
真正消除了逐 token output load/store。增加一个跨 32-token tile 的真实前缀点，
检查尾块和分组；不要复制短输入制造长测试。只有完整 Attention 调用有净收益，
才进入更广泛形状和模型回归。

普通 F16 Attention 同时保留正确性/性能对照，但不强行套用量化 V 的解码方案。
在这些验证之前，不增加专用乘法器、SRAM，不改变 QBEXEC 排空或异常契约。
