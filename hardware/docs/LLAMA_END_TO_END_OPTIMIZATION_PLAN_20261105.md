# 面向完整 llama.cpp 推理的性能面积协同优化

## 1. 目标与结论

目标是以合理的面积增量显著降低 llama.cpp 的首 token 延迟和后续 token 的生成时间，保留普通 RVV 能力。优化对象不限于 QBS/AKV，也不以零新增面积为约束。本文件规定方案选择与验收方法；实际测量结果在相应实验回执中记录，不把设计目标当成实测收益。本阶段不启动综合或物理闭环。

**下一阶段的主要对象应是完整算子调用及相邻算子间的数据传递，而不是单独继续压缩一条 QBS/AKV 指令的周期。** 原因不是专用计算已无价值，而是不同执行区间的剩余瓶颈已经不同：规则投影中 QBS 计算较充分；量化 Attention 中仍有解码、Softmax、输出更新及调度开销。Prefill 则必须同时考虑权重和激活的复用。

执行顺序：

1. 建立完整 token 的周期、数据传输和快速路径选择账目，区分 Prefill 与 Decode。
2. 完成已取得完整调用收益的 Attention 输出驻留集成，并将其纳入后续软件对照，避免重复计算既有收益。
3. 对矩阵驻留/供给、计算吞吐和 Attention 流水三个方向建立资源需求与可消除周期的账目；同时核查激活准备复用的实际缺口。
4. 选择端到端收益最有依据的一项硬件方案。允许增加 SRAM、适量算术或转换通路；共享单元只是候选手段，不是必须满足的形式。

### 1.1 面积预算与选择标准

宽供给候选已推进到可选 compute 及完整命令控制器的部件验收。默认 128 位
路径的 36 项直接/context 周期与原参考全部相同；宽、窄完整控制器在两种
返回节奏下均通过原数值、工作量和故障检查。连续返回的定向集合合计周期
30179 -> 29445，而返回间隔为 3 的集合为 48907 -> 43674。这些结果表明
收益依赖供给条件，不能据此承诺显著模型加速，更不能直接按总线宽度推算。
回执为 `verification/performance/evidence/wide_ingress_20261106_01/result.json`。
下一性能门槛仍是真实 Decode/Prefill 的配对 SDK 区域及同平台 RVV 对照；
实际物理存储、普通 RVV/AKV 和权限边界必须先闭合。若这些实际测量不能达到
后述投入收益目标，应停止扩大宽供给候选，转向驻留/复用或下一主要算子，
而不是把更多部件测试作为端到端目标的替代。

可先以现有完整 QBS+AKV SoC 为基准，将新增约 10%--20% 总面积、代表性完整推理争取达到 1.3x 增量加速作为筛选目标。这不是已确定的硬约束或性能承诺；若某项更大投入具有更高收益，应单独列出取舍。后续面积必须同时给出逻辑和 SRAM，不能只比较新增乘法器。

| 候选 | 要减少的实际成本 | 必须核查的配套资源 |
| --- | --- | --- |
| 矩阵驻留与供给 | N tile 重读激活、重复权重访问、部分和搬运 | SRAM 容量/端口、双缓冲、累积状态及恢复规则 |
| 计算吞吐扩展 | 投影中持续占据关键路径的整数点积 | 格式解码、子组修正、FP 转换/累积、写回速率 |
| Attention 流水与驻留 | KV 解码、Softmax、PV 的串行推进与中间搬运 | KV 布局、head 复用、输出驻留、数值与 mask 边界 |
| 激活准备协作 | 量化、布局转换和多消费者重复准备 | reduction/convert 吞吐、数据版本、生命周期和准入 |

Norm、RoPE、逐元素运算及命令开销均纳入执行账目。如果它们在加速后的模型中成为主要耗时，可以进入硬件候选；不因不属于 QBS/AKV 而排除，也不因容易实现而提前增加专用单元。

## 2. 一个 token 实际经历哪些步骤

当前本地 llama.cpp 的 `src/models/qwen3.cpp` 中，稠密 Qwen3 的主要执行链如下：

```text
输入 token -> embedding
  -> 每一层：
       RMSNorm
       -> Q / K / V 三个投影
       -> Q、K 各自 RMSNorm；Q、K 各自 RoPE
       -> 写入本层 KV cache
       -> QK -> mask/Softmax -> PV
       -> 输出投影 Wo -> residual add
       -> RMSNorm
       -> gate / up 两个投影 -> SiLU 与逐元素相乘
       -> down 投影 -> residual add
  -> 最终 RMSNorm -> vocabulary projection -> logits -> sampling
  -> 下一个 token
```

这张链路图表达依赖，不代表底层实际为每个方框分配独立中间张量。KV 更新、Attention 调度和图融合须继续以当前 GGML backend 的实现为准。

QBS 主要作用于量化权重投影；AKV 支持 Attention 的局部数据组织与复用，并与 RVV 算术协作。不能把 Q/K/V 的线性投影与 QK/PV 两个 Attention 矩阵运算混为一类，也不能因某个 GGML 节点被命中就认为节点全部开销已经消失。

### 2.1 必须分开的三种时间

| 阶段 | 主要工作 | 应报告的指标 |
| --- | --- | --- |
| 冷启动 | 模型装载、页首次访问、权重重排、运行时初始化 | 单独记录冷启动和准备时间 |
| Prefill | 并行处理 prompt token，构建各层 KV cache | prompt tokens/s；首 token 延迟及其测量起止点 |
| Decode | 每次处理一个新 token，读取历史 KV，重复全部层 | ms/token、tokens/s，随实际上下文长度的变化 |

不能以排除准备开销的微内核吞吐替代首 token 延迟，也不能把一次冷启动的 page fault 成本归咎于稳定态计算硬件。

### 2.2 为什么上下文变化会改变优化重点

令隐藏维度为 H，FFN 中间维度为 F，查询头数为 Hq，KV 头数为 Hkv，每头维度为 D。假设 H=Hq*D、Q/K/V 头维度相同，稠密门控 FFN 每层每个 Decode token 的主要投影 MAC 数为：

```text
projection_MAC = 2*H*H + 2*H*(Hkv*D) + 3*H*F
attention_MAC  = 2*L*Hq*D
```

L 是当前实际参与 Attention 的历史长度，而不是配置允许的最大长度。第一个式子包括 Q/K/V/Wo 和 gate/up/down，不包括 vocabulary head；第二个包括 QK/PV，不包括 Softmax。

以本项目使用的 Qwen3-1.7B 形状 H=2048、F=6144、Hq=16、Hkv=8、D=128 为例：

| 实际 L | 每层投影 MAC | 每层 QK/PV MAC | QK/PV 在这两类 MAC 中占比 |
| ---: | ---: | ---: | ---: |
| 128 | 50,331,648 | 524,288 | 1.03% |
| 4096 | 50,331,648 | 16,777,216 | 25.00% |
| 16384 | 50,331,648 | 67,108,864 | 57.14% |

这是运算量估算，**不是周期占比，也不是完整模型占比**。量化解码成本、QBS 与 RVV 算力差异、带宽和 Softmax 都会改变真实时间分布。QBS 加速投影后，Attention 可能在更短的上下文就成为瓶颈。Prefill 应按各 query 的有效因果前缀求和，不能简单按所有 query 都访问完整长度计数。

## 4. 第一优先级：量化 Attention 的输出跨 token 驻留

### 4.1 当前实现与确切缺口

`software/akv/experimental/quantized_kv/register_pv/online.h` 每次产生至多 32 个 token 的 QK scores，然后逐 token 计算在线 Softmax 系数并调用 `quant_register_pv_update()`。

对应 `kernel.h` 已把 Q8_0 V 解码成寄存器向量，避免写出一份完整 FP32 V。但它仍在每个 token、每个 query head 上执行：

```text
load output
-> 必要时按新的最大值缩放 output
-> output += coefficient * decoded_V
-> store output
```

所以当前优化复用的是本 token 的 V，不是整个 tile 的 output。这是源码可确认的流量，不等于已经测得它占多少周期。该路径的启用还受 runtime 配置和准入限制，不能推断所有 Attention 都使用它。

### 4.2 修改方案

把一个 tile 分为两个计算阶段：

1. 保持当前 token 顺序，计算各 head 的最大值、分母和缩放系数；保存每个 token 的输出缩放系数及 V 系数。
2. 将一组 head 的输出载入 RVV 寄存器，按原 token 顺序执行相同缩放和 FMA；整个 tile 完成后再写回。

这么拆分是为了避免逐 token 调用 `expf` 时，编译器因调用约定把向量累加器反复保存到内存。不能只在 C 代码中把变量挪到循环外，就假设它一定常驻 VRF；必须检查反汇编中的 spill 和内层 load/store。

原算法每个 head 的更新是 `y = fma(vs, V, y*ms)`，其中没有新最大值时不执行乘 ms。新算法必须保留这个条件和运算顺序，不能直接改成不同归约树，也不能无条件乘以 1 后宣称严格等价。Softmax 分母也沿原顺序更新。

### 4.3 流量、资源与限制

假设 Hgroup=2、D=128、T=32：

| 项目 | 当前逐 token 更新 | 理想 tile 驻留 |
| --- | ---: | ---: |
| output load/store 的逻辑字节数 | 65,536 B | 2,048 B |
| 两组 FP32 系数的存储 | 每 token 少量临时值 | 512 B，加 rescale 标记 |
| 新乘法器或专用大 SRAM | 无 | 不要求增加 |

65,536/2,048 是这部分指令逻辑流量的比例，不是 DDR 流量或完整 Attention 加速比。系数生成、V 解码和 QK 仍然存在。

VLEN=1024 时一个 D128 FP32 输出占四个向量寄存器。不能同时为八个 head 保留全部输出，否则仅输出就用完 32 个寄存器。首先选择两到四个 head，D256 分维度处理；其余情况按成本选择 fallback。分 head 组会增加 V 的读取或解码次数，必须与省下的 output 流量一起计算。

准入保留当前 finite 输入、RNE、无中途 fflags 观察等约束。验证 output、最终 fflags 和边界行为；不把重新调度后的中间异常时刻声称为任意程序均等价。第一轮用现有真实模型捕获，比较完整调用，而不是只比较 PV 内循环。

## 5. 第二优先级：跨算子的数据准备契约

### 5.1 应复用什么

完整图中存在两类天然扇出：同一归一化激活分别用于 Q/K/V；同一 FFN 输入分别用于 gate/up。它们需要的是“量化准备一次，多消费者安全复用”，不一定要把几个矩阵物理拼接，也不必增加新的矩阵指令。

当前已经有部分跨算子准备复用及 activation context。下一步先核对覆盖范围：格式、激活量化规则、shape、stride、数据版本完全一致时是否命中；输入被下一层覆盖、KV ring 更新或图内存复用后是否正确失效。不能把已有缓存再包装成新的性能收益。

建议由 GGML 的图执行上下文持有准备对象，至少绑定输入版本、维度/步长、量化类型、布局和生命周期。不以指针地址相同作为唯一复用依据。仍保留 NORMAL_MEMORY 准入、单 worker 和错误后禁止不安全 fallback 的要求。

### 5.2 生产者融合的边界

可以研究 RMSNorm 输出准备，或 SiLU*up 到 down 输入量化之间减少临时张量搬运。但是必须保留原来的 FP32 舍入和量化取 scale 的顺序，不能把归一化比例随意移入整数点积。

Q8 块量化通常要先知道整块的统计量；这是读到整块之后才能完成的依赖，不是加一个 streaming 接口就能取消。先采用软件块缓冲和融合循环，只有完整调用中准备成本仍明显时，才评估复用 RVV reduction/convert 的硬件协作。

长 K 的 activation context 装不下时，不能声称全激活常驻。K 分段还涉及多个输出 tile 的部分和保存、累积顺序、fflags 和异常重启。它属于显式状态协议，而不是简单增加一个缓存命中位。

## 6. Prefill：优化完整矩阵的数据流，不只是扩大 M

Decode 中权重通常被单个 token 消费；Prefill 中同一权重块可服务多个 token。因此 Prefill 优化应同时减少权重重复读取和激活重复读取，并避免输出部分和反复提交再载入。

本项目已证明直接 M4 -> M8 不够：M8 使用两个四行 wave，仍共享同样的整数计算能力；它还可能占满两个 activation bank，使原有预取重叠消失。当前结果容量限制会让 N 变小，进一步增加重复读取激活的次数。

下一步应比较两条路线：为有限的矩阵区域制定 activation stripe、weight tile 和输出部分和的驻留调度；或在实际计算受限时增加吞吐。驻留方案严格记录 K 游标，只有所有 K 完成才提交该输出区域。先计算容量与端口需求，再判断能否复用现有空间；新增 SRAM 的容量、位宽和端口均须计入代价。计算扩展则须满足下一节的供给和修正吞吐门槛，不能仅按乘法器数量估算。

对于无法获益的短 K、小 M 或高供给带宽场景，继续使用当前 M4。选择规则应基于形状、profile、容量与测得的供给条件，而不是硬编码 Qwen 型号。现有 M8、QBACC 和 activation context 的结果作为基线，不能重新算作新增机制。

## 7. 如果短上下文仍主要受投影算力限制

应比较**借用空闲 RVV 整数乘法资源**与**适度扩展现有点积通路**。前者可能节省乘法器，但需要完整乘积出口、输入选择及跨 lane 路由；后者增加局部计算资源，却可能有更简单的端口和流水组织。在缺少资源与周期证据前，不将任何一种列为唯一方案。

当前 QBS dot array 有独立的 32 个 8-bit 乘法槽；也有自己的 FP 累积资源。不能说 QBS 当前全部算术已由 RVV lane 复用。Dispatcher 在执行 QBEXEC 前等待普通向量工作排空，这提供了研究互斥借用算术资源的条件，但不自动等于接口已经支持。

有两种不同目标，必须分开评估：

| 目标 | 可能方式 | 主要代价 |
| --- | --- | --- |
| 保持吞吐、降低面积 | 用 lane 乘法器替代部分独立 dot 乘法资源 | 输入选择、完整乘积出口、局部归约、时序寄存器和控制 |
| 尽量少增面积、提高投影吞吐 | 保留当前 dot，并利用空闲 lane 处理额外独立输出 | 更高输入供给、更多在途结果、归约/FP 累积压力和跨 lane 连线 |

普通 RVV e8 VMUL 的架构结果只有低 8 位，而量化 dot 需要完整有符号 16 位乘积。若借用，须在内部完整乘积处取数，不能从普通 VMUL 写回值拼凑。当前共享乘法器的 product 路径提供了静态研究入口，不代表所有构建都已开启此实现或可直接接线。

优先并行独立输出，不拆分同一个输出的 K 累加顺序。要检查 32 对输入/cycle 的现有解码与 SRAM 端口能否提供额外输入，以及 FP 累积是否跟得上。达不到供给条件时，增加乘法资源没有意义。

设计必须保留普通 RVV 的时序和吞吐契约，使用独立 owner/context/epoch 标签处理完成与异常排空。不得为了共享而关闭 RAW/WAR/WAW 检查，或直接去掉 QBEXEC 的全局安全屏障。

按历史投影数据，若仅假设 dot issue 对应的 786432 周期可以减半，其余 315296 周期不变，则 1101728/(315296+393216) 约为 1.555x。**这只是容量变化的乐观算例，不是已证明这些周期可独立减半，更不是端到端模型预测。** 首先验证能否用有限接口代价获取这种吞吐，再决定是否进入 RTL。

### 7.1 不能遗漏的吞吐约束

完整历史 Qwen3 工作量重放还区分了两个重点：当前矩阵候选对应约 99.3680%
的 Prefill 投影 MAC，却不改变 Decode 的 M1 命令；Decode 的 FFN 与词表输出层
分别占量化投影 MAC 的 61.4353% 和 18.0862%。这些不是周期占比。后续不能只
测 QKV，也不能以扩大 M1 乘法吞吐代替权重供给分析。Q4_K/Q6_K 在 32 乘积/
cycle 下分别需要约 18/26.25 B/cycle 的权重数据，而当前 reader 理想上限为
16 B/cycle。完整范围、原数值检查和服务下界的限制见
`LLAMA_MODEL_WORK_LEDGER_20261106.md`；新硬件的实际 reader 效率仍需实测。

现有 `fp_uop_issue` 是 FP arithmetic、I2F cast、half-scale 三条端口成功发射数之和，不是一个单端口的占用周期。不能由该总数直接判断 FPU 是否饱和。子组修正的 pending 周期也只是存在待处理项，不等同于阻塞周期。

新增只读仿真探针 `verification/performance/end_to_end_baseline/projection_resource_monitor.svh` 分别观察三条 FP 发射端口、状态类型、dot issue、子组产出和修正握手。它嵌入已有 compute-engine bench，保留全部参考输出、fflags、计数及故障排空检查；不驱动 ready/valid 或修改 RTL。`run_projection_resources.py` 使用独立 VCS 构建和输出目录，`projection_resources.py` 对原始计数守恒及原测试判定进行独立核对。

在完整 M4、四个输出行的稳态区间，可由 RTL 推导以下资源需求，尚不代表新硬件已实现：

| 情形 | 现有 dot 服务周期/块 | 假设 dot 吞吐翻倍 | 保持现有资源的其他服务下界 |
| --- | ---: | ---: | --- |
| Q4_K/Q5_K，256 元素块 | 128 | 64 | 128 次子组修正需 64 周期；16 输出的 FP arithmetic 共 64 次 |
| Q2_K/Q3_K/Q6_K，256 元素块 | 128 | 64 | 256 次子组修正仍需 128 周期，因此只增加乘法器不足 |
| Q4_0/Q5_0/Q8_0/IQ4_NL，32 元素块，有限 half scales | 16 | 8 | 16 次 cast、16 次 half-scale、16 次 FP arithmetic 各需至少 16 周期 |

这里的服务下界假设端口 II=1、完全重叠，没有计入依赖、存储供给、流水首尾及命令开销。它用于排除明显失衡的方案，不用于承诺加速比。实际探针应验证这些操作数量，再确定是否要增加修正通路、FP 服务能力或采用按 profile 选择的调度。新增算术不能破坏每个输出既定的 FP 累积顺序。

### 7.2 当前端口测量结果

独立 VCS 构建已经完成：36 项既有格式/形状测试，以及从真实 Qwen2.5 Prefill Q 投影捕获生成的 M1、M4 两项切片，共 38 项通过。两项真实数据均保留 K=1536，选取 N=8；它们是同一捕获的不同输入行数，不是两个独立模型。每次执行同时保留原有结果、fflags、计数、四类流水位置故障排空及等待输入时故障取消检查。

| 真实 Q4_K 投影切片 | dot issue | FP arithmetic | I2F cast | 子组修正项 | 完成的块结果 |
| --- | ---: | ---: | ---: | ---: | ---: |
| M1/N8/K1536 | 384 | 192 | 96 | 384 | 48 |
| M4/N8/K1536 | 1536 | 768 | 384 | 1536 | 192 |

例如 M4 的 768 次 FP arithmetic 分别由 192 次 scale、192 次 min-scale、192 次 dot FMA 和 192 次 correction FMA 组成；384 次 cast 则分为 dot/aux 各 192 次。没有将并行端口的发射数相加后冒充 FP 忙周期。该点主 FP/cast 输入反压及整数结果等待均为零；这说明当前配置能服务当前速率，不证明倍速配置仍无反压。

原始结果在唯一验证工作树的 `verification/out/e2e_projection_resources_20261106_01/`。对全部 122 项输入 pin、产物哈希、原始日志和计数守恒再次校验后，精简回执保存于 `verification/performance/evidence/projection_resources_20261106_01/result.json`。检查工具的 5 项测试通过；整个端到端实验工具集合的 27 项测试通过。

这批 bench 的数据递送由测试任务逐 tile 驱动，包含人为等待，因此其总 busy 不能替代实际 SDK/完整投影的延迟；用于吞吐配平的是具体事件数及生产/服务速率。后续不使用这些小规模 busy 数推算模型 tokens/s，也不把上述假设下界称为已经实现的硬件收益。

当前决策是保留“256 元素 K-quant 的平衡计算扩展”作为重点候选：同时考虑 dot、子组修正和 FP 服务，而不是只扩大乘法器。32 元素块格式需要另一种配平，不能无条件沿用。是否优先实现该候选，仍需与矩阵驻留、实际 Prefill/Decode 占比共同判断。

该候选已经形成默认关闭的组件原型，采用格式限定的 64 乘积槽和按输出行归属的四条修正通路。两侧各 38 项配对检查通过；真实 Q4_K M4/N8/K1536 的 compute-bench 区间为 3464 -> 2696 cycles，M1 对照不变。详见 `LLAMA_MATRIX_THROUGHPUT_EXPERIMENT_20261106.md`。这尚未证明整机或完整 SDK 收益，不替代完整命令与模型阶段归因。

### 7.3 Decode 的供给瓶颈不能靠暂存容量代替解决

最新静态复核沿物理路径检查到 `ara_soc.sv`：`axi_to_mem` 为
`NumBanks=1`，仿真 L2 为 `tc_sram NumPorts=1`，数据宽度同样为
128 bit。共享 reader 后面接收全部 AXI 数据，但 block adapter 的输入仍为
128 bit。现有两个 outstanding 与双 weight bank 已提供一定重叠。

对于 M1 的四个输出、一块 256 元素，现有 dot 需要 32 个 issue 周期。
Q4_K/Q6_K 权重分别为 576/840 bytes，匹配这一速率需要平均
18/26.25 B/cycle，而当前物理数据口最多为 16 B/cycle。增加未完成事务
数可以掩盖响应空洞，不能越过这个持续服务上限；增加 panel SRAM 也不能
从相同的单端口口上持续取出更多字节。Q6_K down 的实测严格等待主要
伴随 R transfer，而不是 R valid 长时间缺失，符合这个判断。

因此，候选路线应比较：保持现有物理供给、改进调度所能得到的有限收益；
以及选择性增加真实供给与接纳带宽的资源投入。后者若采用 panel 暂存，
必须同时解决真实内存端口、地址翻译/保护、双路接纳、非对齐残留和 bank
冲突，不能只在 reader 前后加宽连线。初始可考察两个 16 KiB 权重 panel：
每个可容纳 N32、两 K blocks 的 Q6_K，实际 payload 为 13440 bytes；
这只是容量算例，不是已选择的 SRAM 配置或面积结果。

保持当前 R 工作量与 dot 能力时，down 的服务下界为
`max(24576,42532)=42532` cycles；现有 busy 为 49703 cycles。
即使完美调度也只对应约 1.169x 的 busy 上限。若要取得更大的收益，
必须实际改变服务能力或减少真实工作，而不是将这个下界当作一个可达目标。
假设供给足以达到 dot 下界，也仍须计入 FP、激活、descriptor、首尾和
运行时成本，不直接将旧 R beats 除二作为新时间。

### 7.4 真实模型不支持当前无损残差编码方案

对同一 Qwen3-1.7B Q4_K_M GGUF 的全部 197 个投影张量检查了 6720512
个量化块，共 1100961792 bytes。候选保持原量化值和 scale，不重新量化：
Q4_K 保留三个 code bit plane，编码最上两位关系的残差；Q6_K 对两位高码
采用类似变换。块内选择原始或残差编码，加入模式字节、残差存在位图，以及
每八个块的四字节 panel 索引；整个张量无净节省时保留原始格式。

| 格式 | 张量数 | 原始 bytes | 未启用整张量回退的候选 bytes | 最终存储 bytes |
| --- | ---: | ---: | ---: | ---: |
| Q4_K | 168 | 677117952 | 683798313 | 677117952 |
| Q6_K | 29 | 423843840 | 426716861 | 423843840 |
| 合计 | 197 | 1100961792 | 1110515174 | 1100961792 |

全部张量应回退原格式，净节省为零。残差的非零字节过多，局部可压缩块不足以
抵消其他块的模式和索引开销。已检查完整字节恢复和逐张量统计，但这只是
主机端容量研究，不是总线、硬件解码或速度实测；也不证明其他无损编码均无效。
当前方案不进入 RTL。原始输出位于唯一验证工作树的
`verification/out/e2e_weight_supply_codec_study_20261106_01/attempt-02/`。

因此下一项供给方案要在真正的物理数据服务、局部接纳和计算消费之间配平。
只改 AXI 参数、只增加 SRAM，或只增加 outstanding 均不能单独视为完整
实现。若扩展共享存储带宽，对照还应包括普通 RVV 使用相同带宽的情况，区分
通用存储改善与专用机制的增量收益。

宽供给方案与分阶段约束现已写入
`LLAMA_WEIGHT_SUPPLY_ARCHITECTURE_20261106.md`。实现从可独立验证的子模块
开始：未实例化的 32-byte 写入字组装器已通过 16387 个正常场景、四项
clear/reset 和四项非法内部输入检查；实际使用的窄 bank 地址宽度与联合
pending 状态仍需补齐。reader 新增默认关闭的按 range 选择传输宽度，
原 128-bit 两种 MMU 响应模式通过，256-bit 部件的 258 项混合传输与四项
局部故障检查通过。两者均不代表 SoC 已提供 32 B/cycle，也不代表真实
CVA6 PMP、AKV 兼容及完整权重 SRAM 路径已验收。下一步需要把原生格式
映射、组装与真实写端口连接，再推进物理供给和权限边界的整合。

当前不因上述局部瓶颈已成立就立即修改全 SoC 存储。先补足真实模型的
剩余成本账目，比较该项投入与已有 Prefill 计算扩展、Attention 流水的
模型级价值，再选一项主要结构。Norm、RoPE、SiLU/逐元素、KV 更新及
运行时均保留在账目中；暂未测得它们的周期时明确留空，不以 MAC 占比补齐。

## 8. 与已有研究的关系

- [FlashAttention](https://arxiv.org/abs/2205.14135) 的重要启示是围绕存储层级组织 Attention，而不是仅缩短矩阵乘法。本方案的输出驻留借鉴这种 IO 视角；并不声称复现其 GPU 数据流或性能。
- [FlashDecoding++](https://arxiv.org/abs/2311.01282) 同时关注 Softmax 协调、扁平矩阵和数据流选择，说明形状变化下单一固定调度不够。本项目不直接采用其数值调整，也不外推 GPU 加速比。
- [llama.cpp 的 SpacemiT 支持](https://github.com/ggml-org/llama.cpp/blob/master/docs/build-riscv64-spacemit.md) 区分 RVV 与 IME1/IME2。值得借鉴的是运行时接入、布局和内核选择的完整配合，而不是单独增加一条运算指令。本项目更应考虑如何利用已有 RVV 资源，控制额外硬件规模。

## 9. 如何确认真正改善了端到端性能

先固定当前交付软件/RTL/编译选项，不将本地未提交变动混入基线。QEMU 可检查完整模型的选择和数值，不用于预测真实 RTL 周期。

### 9.1 分层测量，避免长时间盲跑

| 层级 | 要证明的事情 | 最小有效实验 |
| --- | --- | --- |
| 静态账目 | 哪个图节点重复准备、复制或退回 | 一次真实模型图与 runtime 选择记录，含 shape/type/stride/拒绝原因 |
| 定向正确性 | 新顺序和状态生命周期正确 | 真实输入、尾块、head 分组、mask、错误前置拒绝及相邻普通 RVV |
| 完整算子 | 优化没有把成本转移到准备或提交 | 同一 ELF 配对完整调用，含首次准备、所有 tile、最终归一化/写回 |
| 层或子图 | producer-consumer 复用有效 | QKV 或 gate/up 共享输入区域；Attention 含 KV 更新和输出转换 |
| 完整模型 | 用户等待时间确实下降 | 固定 prompt、生成长度、KV 类型和线程设置的板端对照 |

VCS 优先选真实捕获中的中等规模完整调用，保持完整 D/K 和非重复的数据。先由短试测的仿真速率估计时间，将每项控制在约三小时内；不为了完整模型启动长时间 VCS。裁剪 KV 长度或输出行时明确外推限制。超过十分钟的任务后台运行，不频繁轮询。

### 9.2 端到端账目

计时的一级区间应互斥：输入准备、各层投影、Attention、其他逐元素/归一化、输出 head、采样和运行时。区间有融合或并发时按父子关系记录，不能把子项再次加到总时间。QBS busy、reader busy、RVV activity 等重叠事件只用于解释，不直接相加成 stall breakdown。

对于剩余等待，关注可判别的事件：命令接受/结束、当前 tile 所有权、输入 ready、AXI AR/R 握手、输出 load/store 次数、向量发射/退休、VRF 返回阻塞、软件准备起止。先说明探针语义，再由周期窗口判断因果。

若某一段占当前完整时间 p，新机制令该段加速 s，而新增协调成本占原总时间 d，则模型收益为：

```text
speedup = 1 / ((1-p) + p/s + d)
```

p 必须来自同一版本同一模型配置的测量。例如占比 20% 的阶段即使加速两倍且无新增成本，总收益也只有 1.111x。不能把微内核几十倍加速再次套用到已经启用 QBS/AKV 的完整模型。

### 9.3 补齐真实归一化成本，而不削弱基线

源码复核确认，当前 GGML 已融合 RMSNorm 与权重乘法；SwiGLU 也已有
RVV 路径。后续测量不得拆开前者或把后者改成标量代码来放大收益。
RMSNorm 的平方和仍在源代码中逐元素以 FP64 累加，适合先评估复用现有
RVV 有序宽化规约，而非直接增加新的算术单元。

隔离候选保留 FP32 平方、原顺序 FP64 累加以及后续全部融合运算。
已从同一真实 GGUF 重建四个 Prefill token 和首个 Decode token 的输入，
并由原始融合函数逐位复现全部 10240 个捕获输出。该主机核验只证明输入
与基线一致；目标周期、候选正确性和完整模型收益仍是独立门槛。
实验入口与语义见 `software/rvv/experimental/ordered_rms_norm/README.md`。

普通 RVV 函数返回不自动等于最后的向量存储完成。该实验将等待 backend
idle 的向量 CSR 读取纳入结束时间，并计入其开销，不用裸函数返回时间
冒充完整调用。FP64 原始和也单独比较，避免最终 FP32 舍入掩盖重排错误。
即使此处取得加速，也不能据此声称 Norm 已成为整模型的主要瓶颈，或停止
权重供给、Prefill 数据流和 Attention 的整体评估。

## 10. 结束与保留标准

下面是建议采用的工程门槛，不是既有测试结论：

- 软件优化：完整算子在两组不同真实形状上有可重复收益；无收益形状可保留原路径，不能以隐式降精度获得加速。
- 小硬件优化：先要求目标完整算子有约 10% 以上净收益的可信依据，再投入 RTL；若仅有约 1% 的局部理论空间，优先不做。
- 所有优化：输出/最终 fflags 满足约定，异常和取消不泄漏部分结果，普通 RVV 无回归；复杂度与新增状态明确可验证。
- 面积：软件驻留方案不要求新增算术单元；新增 SRAM、仲裁或借用 lane 的接口须列资源清单。不能在无综合结果时宣称“面积为零”或给出确定门数。
- 端到端：分别报告 Prefill、Decode 和上下文长度。完成真实模型对照后再报告总体加速，不以调用覆盖率代替时间占比。
- 基线：普通 RVV、当前已交付 QBS+AKV、拟保留的软件优化和新硬件增量分别固定身份。不得把旧机制的累计收益再次计为本轮新增收益。
- 决策：同等工作量下给出原始周期、数据搬运、数值及 CSR 检查。无收益或回退的形状明确保留旧路径，不以隐式缩小模型工作量换取结果。

近期节点是：完成 M1 提交实现的非 M1 性能回归，
收齐真实 RMSNorm 的完整调用与数值检查；这些结果用于确定软件基线，不
作为主要硬件工作完成的替代证据。结合已经完成的全 N Prefill、真实
Decode 供给测量及完整模型工作量，继续比较可提高真实供给速率的结构、
矩阵复用与 Attention 流水。输出驻留、三类 FP 端口测量、M1 ABBA 以及
trace-context 与 SDK-dispatch 模型功能配对已经完成，不再列为待做。当前无损残差编码
因真实模型没有净节省而淘汰，不投入解码器资源。

## 11. 持续目标

面向端侧 llama.cpp 完整 LLM 推理，以现有 RVV 处理器及 QBS/AKV 为基础，研究并实现具有较高性能面积收益的软硬件协同优化。依据真实模型的 Prefill/Decode 归因选择优化点，允许合理新增计算、存储和流水资源；完成实际运行时集成、模型功能及代表性 VCS 性能验证，保持普通 RVV 和 fallback 正确，并检查跨模型、格式、尺寸与上下文的适用性。本阶段不进行综合、功耗或物理闭环。
