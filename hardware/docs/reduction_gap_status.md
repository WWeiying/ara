截至2026-10-11，工作分支为 `reduction-optimization`，测试构建的提交基点为 `d93d088d`；实际受测增量由冻结源码哈希标识。显式候选配置为 `hardware/config/reduction_completion_4lane.mk`，采用4 Lane、VLEN=1024。下文区分已通过的独立阶段与已完成的106程序最终组合，旧版本通过记录不自动覆盖新RTL。历史过程与原始路径保存在 `reduction_completion_engine.md` 和 `reduction_gap_progress.json`。

## 外部seed的当前协议边界

外部seed从Load/Slide缓冲出口的实际VRF接收事件捕获，携带生产者ID、基址寄存器、版本、数据和有效字节。只捕获基址首字，消费者必须通过版本和位宽覆盖匹配。生产者的架构生命周期及目的寄存器相关性仍要等正常完成，首字到达不等于整条指令完成。

这一外部seed扩展作用于 `word_chain_eligible`：整数/逻辑/极值和适用Word浮点路径。FP16/FP32精确无序求和仍使用原有独立seed协议，不能从外部seed测试推导它也获得相同扩展。

当前派发资格限于非Mask、非重启、非Fault-only-first且nf=0的VLE，以及非Mask、非重启的VSLIDEDOWN。其它生产者形态继续走正常依赖。全Mask Load/Slide保留旧seed的回退已测试；这不表示已经为Masked生产者实现提前seed绑定。寄存器组内部非基址seed不能误用基址缓存，源向量RAW和目的WAW也不得随seed一起放宽。

## 保留限制与负面实验

中央结果背压时尚未启动通用后台计算；现有八程序观察仅有1个后继源与seed已齐的可利用周期，未据此增加结果检查点。Word与SLDU同周期退休原型曾完整运行但使测量窗口344→351周期，已撤出推荐RTL并保留复现补丁。同VFU普通算术Late Seed实验也出现1386→1482周期退化，默认关闭。这些限制或负面结论应如实保留，不能以“局部少一次等待”替代整段程序的收益证据。

## 复现与可保留证据

`hardware/config/reduction_completion_regression.json` 保存最终组合的106个程序名，内容与本次已完成的冻结运行清单一致。先按仓库工具链说明编译这些应用，使用显式候选配置构建模拟器；本轮直接使用的VCS冻结构建及其依赖哈希保存在各阶段source manifest中。以下命令用于已经构建好的候选模拟器，`--out` 必须选择新目录以保留旧证据：

```bash
python3 hardware/scripts/run_reduction_audit.py \
  --sim /absolute/path/to/candidate/simv \
  --out hardware/build/rce/reproduction_full \
  --jobs 8 --timeout 2400 --sim-arg +RCE_STALL_PROFILE \
  --apps-file hardware/config/reduction_completion_regression.json
```

回归运行器会在启动前冻结ELF，检查Core成功标志、失败/断言标志和退出状态；读取历史结果时还需用 `summarize_reduction_stalls.py` 的 `read_suite` 核验哈希与日志分类。单项消融应只修改相应开关，并使用同一组已冻结ELF；不要在不同源码或ELF之间仅凭应用名称比较周期。

`reduction_gap_evidence.json` 保存已结束阶段的逐项ELF/日志/模拟器哈希、程序数量和测量窗口；它是便于保留和核对的摘要，不包含原始日志，也包含最新106程序的独立通过证据。未做综合和真实时间评估；标准Make配置的变量展开已检查，不把它描述为另一次已完成的标准Make构建。

当前相对于提交基点修改的8个功能SV文件均与已完成106程序回归的冻结输入逐字节相同，列表及哈希已纳入 `reduction_gap_evidence.json`。这项检查不把测试观察器当成功能RTL；周期观察器的issue-ID归因修正单独记录。宽化整数及浮点规约的派发解码先将 `vtype.vsew` 规范化为结果位宽，因此Late Seed的生产者位宽比较和RCE字节覆盖检查使用的是宽化后的seed位宽，并非原始源元素位宽；本次复核没有因此修改RTL。

## 下一阶段：精确路径的外部seed与接收解耦（尚未实现）

106程序验收完成后，源码复核确认两处独立限制。首先，`ara_sequencer.sv` 对精确消费者仅接受 `writer_exact_q` 生产者；Word路径新增的普通和外部生产者资格没有接入此分支。其次，`reduction_completion_engine.sv` 的精确包头接收条件为所有Lane包头匹配且 `exact_late_seed_ready`；seed在这里锁存，而不是等全部精确状态接收结束后才绑定。因此“局部源计算可以提前”不能推导出“全局精确合并也完全不等seed”。这是控制与数据归属上的实际限制，收益仍需测量。

现有 `rce_exact_command_t` 仅含消费者ID、目的寄存器、版本及late标志，不含seed生产者元数据；匹配由SLDU的 `exact_result_cache_*` 完成。该缓存依靠精确生产者在SLDU内的顺序处理保留旧值，Word缓存则在生产者ID进入新生命周期时失效。若直接开放普通生产者并复用一个按ID查询的缓存，排队的旧消费者可能在读取seed前遇到ID复用。因此实现必须在消费者上下文中保存已匹配的seed，或证明并约束对应缓存条目的保留期限；不能只扩大准入条件。

拟采用消费者描述符携带生产者ID、寄存器版本及有效位宽，并为在途精确消费者保存32位seed快照和valid位的组织，复用实际VRF写回捕获端口。对精确结果生产者保留现有协议兼容路径。包头和精确分段接收可在独立seed快照尚未就绪时继续；最终计算必须等正确seed快照到达。FP16原始位模式、宽化到FP32的seed位宽、全Mask和特殊值处理不能从FP64 Word协议直接照搬。该方案目前只是待实现设计，不属于106程序验收覆盖的新增能力。

新增 `perf_rce_exact_load_seed` 与 `perf_rce_exact_slide_seed` 在FP32、LMUL1下覆盖VL=1/4/16/32，每窗口16对生产者与规约。Slide探针在测量前初始化整个源寄存器，保证VL=1时被滑入的元素也为预期seed。基线使用已验收的功能RTL及修正发射ID归属的只读观察器，目录为 `hardware/build/rce/gap_exact_external_seed_baseline_v1`。此时现有FPU握手观察器不能直接作为精确累加器接收事件，后续必须增加精确输入和包头/分段接收观察，不能冒用Word FP64的局部计算证据。

上述两个基线程序已通过，冻结ELF、模拟器和日志已核验。按VL=1/4/16/32，Load窗口为463/436/470/500周期，Slide窗口为397/360/388/422周期。两程序各观察到64次规约派发，均携带非零seed hazard，late标志均为0；这证实当前外部seed提前绑定没有覆盖精确路径，但尚不能量化移除等待后的收益。
