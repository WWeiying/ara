# 当前 Q8_K 投影的优化优先级

本报告复用已验收的 VCS 原始日志，不新增仿真，不修改正在运行的
signed-max 对照程序。范围是实际模型数据的 M4/N1536/K1536 Q4_K 投影，
不是整个 GGML 算子或端到端模型。

## 周期归因

来源：`verification/qbs/results/q8k-current-projection-acceptance-20261026.json`。
分析器 `verification/qbs/analyze_projection_phases.py` 校验原始日志哈希，
按日志顺序将每组 48 条成功 QBS 命令关联到相应投影试次，并逐命令验证
互斥阶段之和等于忙周期。以下是已接受的向量准备版本，两次试次合计。

| 部分 | 周期 | 占完整测量区间 |
| --- | ---: | ---: |
| 计划构造和上下文适用性检查 | 4,949 | 0.45% |
| 激活量化准备 | 392,004 | 35.29% |
| QBS 引擎忙周期 | 670,471 | 60.36% |
| 执行区间中不属于引擎忙周期的部分 | 43,410 | 3.91% |
| 总计 | 1,110,834 | 100% |

最后一项不能全部叫软件开销。它还包含指令投放、完成、结果存储以及
计时/CSR 探针；需要更细的信号才能继续分解。QBS 命令是阻塞执行的，
本测试每次执行区间恰好包含 48 条命令，因此可以相减。

结论：继续优化激活量化是合理的。即使完全消除执行区间中的引擎外
部分，也只相当于当前切片约 3.91% 的周期；这不是优先重写 SDK 的依据。
这些比例不能推广到不同 M/K 或整模型。

## 不能从计数器直接推出的结论

`qbs_engine.sv` 使用互斥的 command_phase 分类。
计算阶段为 394,872 周期，计算与读引擎活动并存的阶段为 222,600 周期。
后者的条件是处于计算阶段，同时 read_busy 或权重范围请求有效，
并不保证该周期总线上有有效数据传输。

`useful_pairs == pair_capacity == 18,874,368` 只说明实际点积投放周期内的
元素槽位没有因当前形状而浪费。`qbs_profile_engine_int.sv` 在
`compute_active_q && issue_active_q` 时才累加这些数值，故不能称为
全周期计算利用率 100%。

`fp_table_full_cycles = 248,832` 是诊断信号，不可当成可以直接消除的
独立停顿，更不能与其他阶段相加。需要同时查看输入是否有效、发射是否
被阻止和依赖状态，才能判断扩大表项是否有收益。

## 激活复用的实际边界

每次投影读取的激活逻辑字节数为 336,384，即 48 × 7,008。
四行激活超过当前 4,672 字节上下文容量，因此本测试是 direct 路径。
这确实存在重复读取，但单独激活阶段两次合计仅 8,160 周期，占总周期
约 0.73%。它不是全部激活访存成本，也不是扩大上下文容量的加速上限；
仍不能仅依据重复字节数就承诺显著性能收益。

现有 llama.cpp 后端已经对合适的 M1 共享输入实施跨算子上下文复用，
且会跳过重复量化。不得把它重新包装成待新增优化。M4 软件量化缓存则
需要独立存储和严格生命周期，目前尚无实际共享输入轨迹证明其收益。
FFN down 的输入与 gate/up 不同，不能因为 K 较大就认为可以共享准备结果。

## 当前决策

1. 完成正在运行的同 ELF signed-max 对照，测量新候选相对已接受向量
   准备版本的增量收益，同时保留字节、CSR、独立输出参考和写回检查。
2. 有明确收益后，再做默认跨算子上下文开启条件下的 GGML/模型共存
   验证，避免只证明隔离开关下正确。
3. 若继续优化硬件，先定位计算阶段的实际发射和依赖空隙，不因表满
   计数高就直接扩容；不能用本报告的占比代替周期级根因证据。
4. Attention 的 grouped-PV 当前仍比普通路径慢约 0.97%，继续默认关闭。
   不以局部搬运减少为由启用整体变慢的路径。

本轮没有改变生产量化算法、硬件容量、指令语义或运行时默认选择。
