# 共享 SIMD 整数乘法器

## 范围和状态

本实现只修改 lane 内整数乘法路径，不修改浮点运算、QBS、AKV、访存或软件。
编译时定义 `ARA_SHARED_SIMD_MUL` 启用共享核心；不定义时使用原来的四组乘法器。
在面积、时序和整机回归完成前，不将共享实现设为默认，也不替换 FPGA 交付副本。

2026-11-03 选择保留 `shared_mul_ppa_booth_20261102_01` 对应的 Booth+Dadda
版本，当前乘积核心恢复为其封存源码。局部面积 20838.383837 平方微米，
相对原整数乘法器组减少 35.7163%。虽比 arithcsa 版本多约0.65%面积，
但 COMBO setup 违例较小（-0.15 ns 对 -0.20 ns）；因此保留较均衡版本，
不是宣称已完成时序签核。clk_i setup 裕量接近零，仍有94条 hold 违例，
最差 -0.07 ns，以及不可行路径告警待核查。保留其他候选的封存输入、
VCS日志和综合结果，不再追加局部试验。

选定版本已完成完整 SoC 的本轮功能与应用周期对照：16类乘法/乘加指令、
96阶段混合SEW定向程序、整数点积9个计时点、矩阵乘法4至128阶、真实
llama.cpp六项微内核全部配对通过。所有21个应用计时区间周期逐项相同，
各Lane请求/完成数量与阻塞计数一致；没有观察到共享资源引入额外停顿。
范围、原始证据、超时记录及仿真构建优化见
`verification/timing/SHARED_MUL_SOC_ACCEPTANCE.md` 和 `shared_mul_selected.json`。
这不替代物理时序、功耗、完整软件生态或 FPGA 板测验收。

## 共享什么

原实现按 SEW 分别生成 8 个 8 位、4 个 16 位、2 个 32 位和 1 个 64 位乘法。
同一个 lane 每次只向其中一组送入有效操作数。
新实现将这些互斥的乘法合并为一个可分区的部分积网络和进位保存压缩树。

| SEW | 每个有效输入的运算 | 完整乘积总位数 | 内部乘积寄存器级数 |
|---|---|---|---|
| 8 | 8 组 8×8 | 128 | 0 |
| 16 | 4 组 16×16 | 128 | 1 |
| 32 | 2 组 32×32 | 128 | 1 |
| 64 | 1 组 64×64 | 128 | 1 |

这里的级数不包括 VMFPU 入口寄存器和结果队列。16/32/64 位使用同一组寄存器，
8 位绕过该寄存器。单一位宽无背压时可每周期接受一个 64 位操作数对，不通过
串行执行换取面积。混合位宽切换必须服从共享资源和结果顺序，不能再把四套
独立流水的全部 ready 信号视为共享实现的逐周期契约。
实际最高主频和应用性能尚需验证。

这不是将 8 个完整的 8×8 乘法器串行复用成 64×64。
完整 64×64 运算需要所有交叉部分积；只保留 8 个小乘法器无法同时保持原吞吐。
以 8 位为最小 SIMD 分区，共享内容包括带符号部分积、压缩树、最终乘积加法器、
一套乘积流水、一个后处理加法器以及最终饱和选择。符号修正已并入部分积，
不再串联两个乘积高半部减法器。最终乘积加法和输出侧乘加仍为独立电路，
不能为了进一步复用而破坏每周期吞吐。
不同位宽仍需各自的静态取位、边界判断和舍入条件，但不再各自生成宽加法器。

## 算术逻辑

当前候选在 `simd_mul_shared_product.sv` 内采用分区 Radix-4 Booth 编码。
每个 N 位元素按每两位乘数一组读取 `{b[q+1], b[q], b[q-1]}`，选择
0、+A、+2A、-A 或 -2A。每个元素的第一组强制 `b[-1]=0`，不读取前一元素。
整个 64 位 lane 始终只有 32 个编码组，不是四套独立 Booth 乘法器。

每个编码组产生 N+2 位的部分积，足以容纳无符号 A 的两倍及其负数。
负部分积先按位取反，所需的加一移到修正行，不在每组内部串联加法器。
为避免把每行的符号位重复填充到整个乘积高位，将该行最高位取反，并加入
与数据无关的常数偏移。对一个元素，令 W=N+2，局部分组位置 q=0,2,...,N-2：

```text
M_q = 0、A 或 2A，以 W 位表示
T_q = (M_q XOR {W{negative_q}}) XOR 2^(W-1)
C   = -sum_q 2^(W-1+q)  mod 2^(2N)
P   = sum_q (T_q << q) + sum_q (negative_q << q) + C
```

`T_q` 按无符号数进入压缩树。最高位取反带来的偏移由 C 抵消，因此不需要
对每一行做长距离的重复符号扩展。每组负号修正的加一位落在元素低 N 位，
C 只占高部且与这些位不重叠，两者可放入同一修正行。

N/2 组 Booth 编码把 B 当作有符号 N 位数。若 B 应为无符号且最高位为1，
还需增加 `A << N`，截断在该元素的 2N 位内。它放在另一条修正行中，也适用于
有符号 A 与无符号 B 的组合。共 32 行 Booth 部分积、1 行负号与常数修正、
1 行无符号最高位修正，即 34 行，不使用多周期串行乘法。

压缩网络按各列实际高度采用 Dadda 调度，目标列高依次为
28、19、13、9、6、4、3、2。列高包含该列可能存在的修正位。
只有需要降低列高时才放置全加器或半加器；未使用的数组位是编译期常量零，
不构成寄存器或运行时调度硬件。全加器和半加器产生的进位进入下一压缩级的
相邻列，不允许在同一级内继续传播。最终两行进入分区进位传播加法器。
此调度没有增加流水寄存器，也不改变每周期接收一组操作数的接口。
按当前支持位集合静态计算，压缩调度包含 2055 个全加器位置和 87 个半加器
位置；上一逐位 Dadda 调度为 3872 个全加器位置和 91 个半加器位置。
这些是综合前的结构数量，不是最终标准单元数；Booth 编码和选择的新增成本
必须一起计入同约束综合，不能用全加器位置减少比例代替面积减少比例。

此时中间和可能溢出 2N 位，因此每级压缩器必须丢弃跨元素边界的进位。
当前保留版本使用八个 16 位片段和三级组进位前缀
网络。组传播在 2N 位边界清零，组生成保留；这样只阻断前一元素的进位，
不丢弃本元素产生的进位。最终加法恢复由片段和计算组传播的原表达式。
压缩器采用原来的 XOR 求和及多数函数进位表达式；carry 只进入下一级
相邻列，不产生级内横向进位链。
不能沿用旧无符号树中“完整乘积不溢出，所以不需要隔离”的假设。
VMULHSU 的 signed 标志遵循现有端口方向：内部 B 为有符号源，A 为无符号源。

`simd_mul_shared.sv` 保存乘积、C 操作数、mask、饱和位、操作码和 SEW。
输出侧选择乘积的低半、高半或定点小数部分，统一送入
`simd_mul_partition_add.sv`，完成乘加、乘减或舍入增量。
这个加法器由八个字节片段和三级字节进位前缀网络构成，元素边界切断前一元素的
进位，并注入该元素自己的减法初始进位或舍入位。
饱和时输出相应位宽的最大正数。
旧 `simd_mul.sv` 和它的外部乘积选项保留供对照，不实例化在新共享路径中。
VXRM 保持原来的输出侧可见语义，本次未更改 CSR 时序契约。

## 接入与握手

共享核心读取 VMFPU 已寄存的公共 A/B 和操作码。
位宽来自与它们同步的 `vmul_simd_in_valid_q` 单热标签，不能使用可能已经
指向下一条指令的 issue 状态。当前恢复由单热标签编码二进制 SEW 的接口，
用于部分积选择、边界隔离和流水记录。四种部分积操作数由常量连接和模式
选择组成，不保留 opt123 的逐位拆解及外部 one-hot 核心端口。
有效请求进入唯一的共享通路。
输出的 SEW 随乘积保存，由它生成原 VMFPU 所需的单热结果有效信号。

背压由共享流水传回入口；入口停顿时操作数和有效标签保持不变。
8 位旁路仅在共享流水为空时生效，不能越过尚未取走的宽位结果。
无有效入口时必须仍允许入口寄存器装入新请求，不能因默认 SEW=8 而错误地
等待 8 位出口 ready；这一条件显式体现在 ready 逻辑中。
不同位宽的结果仍按原有顺序控制读取，本次不解除跨位宽发射限制。

读取了下一周期的输出有效位。后者通过先保存时钟沿的输出快照修正，未修改 RTL
来迎合测试；原失败日志也保留。最终 r3 使用修正后的检查器运行通过。

独立算术模型检查九种内部操作、四种舍入模式、符号边界、饱和、随机数据、
反压及复位；固定流水测试逐周期检查 valid 和 ready，并在有效时检查结果、mask、
vxsat。混合位宽测试按实际接受顺序排队，用旧乘法器检查退休值，另检查事务无丢失、
无乱序，以及每种位宽连续 256 次发射的 II=1。

`extract_shared_mul_bank.py` 还可直接提取 VMFPU 实际修改的乘法器实例和选择逻辑，
生成小型测试包装，避免手写测试接线与实际接线不一致。包装替代了输入隔离单元，
不包含整个 VMFPU 的发射、时钟门控和结果队列，因此不能替代整机回归。

## 复跑

在项目根目录执行；每次使用新的 BUILD 目录：

```sh
make -C verification/timing mul-check \
  REFERENCE=f636824e9b5a347666401bba40a6a17925b9a402 \
  MUL_DEFINES=+define+TEST_FULL_SHARED_SIMD_MUL \
  BUILD=/absolute/path/to/new-test-output
```

动态位宽测试目标为 `shared-mul-bank-check`，VMFPU 语法分析目标为
`shared-mul-vmfpu-analyze`。普通 `mul-check` 不传 MUL_DEFINES 时检查旧路径。

实际接线测试示例（`OUT` 必须使用新的独立目录）：

```sh
OUT=/absolute/path/to/new-bank-output
python3 verification/timing/extract_shared_mul_bank.py \
  hardware/src/lane/vmfpu.sv "$OUT/extracted"
make -C verification/timing shared-mul-bank-check \
  REFERENCE=f636824e9b5a347666401bba40a6a17925b9a402 \
  BUILD="$OUT" MUL_DEFINES=+define+ARA_SHARED_SIMD_MUL \
  MUL_BANK_TOP=shared_mul_stream_tb \

```

## 面积和时序验收

共享逻辑并不自动意味着面积更小。SEW 路由、多级压缩、最终宽加法和边界隔离
均有成本；Booth 编码也会引入倍数选择和修正逻辑，综合器对原 `*` 的优化
可能比显式逻辑更好。必须使用同一工艺库、约束、负载比较整个整数乘法子系统，
包括选择器、流水、后处理和门控，不能只比较乘法核心。

首轮同约束 DC 实验位于验证目录 `shared_mul_ppa_20261101_02`。基线最终
cell area 为 32416.271510 平方微米，clk_i setup 违例为零，但仍有其他路径组
和 hold 违例。共享旧版在 3600 秒超时，无最终映射报告；延迟优化过程中面积
从 25899 增到 40358.6，最后最差负裕量幅度为 0.22 ns。这些是中间统计，
不能作为共享版最终 PPA，也不能据此承诺压缩收益。

首轮 `metrics.tsv` 中 area 字段为空，基线面积以 `area.rpt` 为准；自动汇总
尚未产生有效比较。预编译 resources 报告中的 4225-bit 四选一 MUX_OP 是
展开结构信息，不是最终门数，也不是重排交叉开关的证据。

符号修正融合版本的完整局部 DC 结果位于 `shared_mul_ppa_bw_20261102_01`：
基线面积 32416.271510 平方微米，共享版 29970.191922 平方微米，减少 7.55%。
两者 clk_i setup 违例均为零；共享版仍有一条 COMBO setup 违例（-0.20 ns）
和 89 条 hold 违例（最差 -0.08 ns），不能称全部时序闭合。
共享版的压缩树及最终乘积加法器占 21411.0959 平方微米，即子系统的 71.4%。
这构成改造压缩树的依据，而不是直接承诺 Dadda 候选会取得某个面积收益。

Dadda 对照版本结果位于 `shared_mul_ppa_dadda_20261102_01`：共享版面积
27676.991839 平方微米，相对同一基线减少 14.62%；clk_i setup 零违例，
仍有一条 COMBO setup 违例（-0.15 ns）和 90 条 hold 违例（最差 -0.08 ns）。
压缩树及最终乘积加法占 19389.2159 平方微米，即子系统的 70.1%。
这说明主要成本仍在部分积求和，因此下一步评估减少部分积行数的 Booth 候选。
Booth 对照版本 `shared_mul_ppa_booth_20261102_01` 已完成局部综合：共享版
20838.383837 平方微米，相对同约束基线减少 35.7163%；clk_i setup
slack 为 +0.0000343323 ns。仍有一条 COMBO setup 违例（-0.15 ns）和
94 条 hold 违例（最差 -0.07 ns），且有 infeasible-path 告警待核查。
共享版耗时 2681 秒，基线 1447 秒。这些数字对应当前恢复保留的封存
版本；与实际应用周期验收互为独立证据，不构成完整时序签核。

完整 SoC 的本轮乘法相关程序及应用周期回归已完成，FPGA 验收尚未完成。
局部面积减少35.72%不能解释为整芯片面积减少35.72%；应用周期对照证明
被测程序无观察到的性能损失，而不是应用加速。
