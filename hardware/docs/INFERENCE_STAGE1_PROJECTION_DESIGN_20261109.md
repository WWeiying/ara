# 阶段1方案收敛：投影输出块的有界合并

状态：**完成结构审查与旧轨迹筛选；N64降为待筛候选，暂不进入RTL实现。**
当前实施顺序已在[最终计划](INFERENCE_STAGE1_FINAL_PLAN_20261109.md)定案。
依用户要求，本文所列低扰动计时待测项不再阻塞阶段1规划；未通过的工具门槛不改写。
本方案基于[整模型板测返回](INFERENCE_STAGE1_BOARD_RETURN_20261109.md)，替代此前
“默认先做驻留QK/PV”的优先级假设。五个阶段编号不变；阶段2/3的机制取舍需要按
阶段1证据更新，不按原先讨论顺序强行实施。Decode低扰动计时与命令边界成本仍待闭环。

## 1. 选什么，以及为什么不选其他方案

本文件考察**M1输出块有界合并**：一条显式的新命令覆盖相邻两个N32输出块，
即最多N64；继续复用当前QBS算术、reader和VRF结果通路。它是新的命令组织，
不是简单启用已有M8、扩大MAC阵列或另建DMA写引擎。

| 方向 | 判断 |
|---|---|
| M1/N64输出块合并 | 结构可行，但旧轨迹尚不支持显著收益首选；保留为待筛项 |
| 共享FPU驻留QK/PV | 保留；先关闭PV两项边界错误，短上下文模型份额不足以成为默认首项 |
| Prefill多行/跨N复用 | 第二研究项；已有M8不等于新机制，需同时解决激活装载代价 |
| 激活量化直填 | 后备项；只加入口不能消除归约、scale和转换，先测真实可消除份额 |
| 普通异步命令FIFO | 不选首版；CPU阻塞协议不能自动提供下一条命令 |
| 扩大MAC或总线 | 不在本轮范围；不能用资源翻倍代替对供给与边界的归因 |

Prefill中FFN占约60.7%，但M1合并不能解决M4主体。本文件仅讨论资源复用明确、
语义有界的Decode候选；Prefill的双输入复用独立评估，不假称一项覆盖全部。

### 1.1 旧SoC轨迹给出的筛选结果

已离线重放通过验收的Q6_K/M1/K2048/N64切片，不运行新仿真。两次执行各含两条
N32命令。退休CSV必须只使用`event=retire`；其中的load/write等事件常带PC=0，
不能误认为函数退出。native入口/返回由冻结ELF符号及实际ret指令确定。
engine的完整fire/terminal来自原始日志；`boundary.csv`只是首个有界窗口，不含
所有terminal，不能用它冒充完整命令记录。

| execute内部互斥区间/周期 | 第一次 | 重复调用 | 均值 |
|---|---:|---:|---:|
| execute入口至首条native函数入口 | 1411 | 1266 | 1338.5 |
| 两次native函数中的engine busy | 8247 | 8242 | 8244.5 |
| 两次native函数中的非busy区间 | 259 | 234 | 246.5 |
| 两次native函数之间 | 315 | 275 | 295 |
| 末次native返回至execute计时结束 | 81 | 81 | 81 |
| execute合计 | 10313 | 10098 | 10205.5 |

这解释了此前1961周期`execute-busy`残差：其中1338.5周期位于一次性的入口/首条
准备区间，占约68.3%，不是每命令重复付出。该区间包含参数、容量、对齐、scope及
token检查和首条命令准备，但未逐段计时，不能全称为检查时间；`t2`之前的建plan
也不在此区间内。SDK已经采用首尾准入优化，不能再次假设它遍历全部N tile。

native函数的非busy平均为123.25周期/命令。将一次中间间隔与一份native非busy
作为筛选预算仅约418.25周期，且不保证全可省。即使宽松地删去入口前缀之外的
全部622.5周期残差，再删去第二条命令的176周期activation phase，也仅798.5周期。
176已包含160周期context replay，不能将二者再相加。

这个798.5不是整个新结构的严格收益上界：它把仍需保留的store等也理想化删除，
又没有覆盖任何改变权重调度带来的额外收益。它足以削弱“大量重复CPU边界”这一
首选理由，却不能跨SoC到Linux/DDR外推为所有模型/形状都不可能快5%。
**结论是暂缓首选地位，而不是直接实现后再寻找有利结果。**

可复核工具为`verification/performance/next_mechanism/stage1/replay_native_boundary.py`；
结果位于验证工作树`verification/out/stage1_native_boundary_20261109_02/`。
它核对冻结ELF、原始日志/CSV哈希、UVM回执、完整命令边界及原有execute分区，
并将分析器源码随结果封存。没有将旧SoC周期写成新板卡周期。

## 2. 原路径中的边界

冻结软件中，GGML GEMV/GEMM先创建plan和workspace，再由SDK cursor遍历N tile。
**plan不是每条native命令重建。** 每条命令仍要选择activation access、生成描述符、
调用executor，再执行以下原有指令序列：

```text
fence rw,rw → vsetvli → QBEXEC → vsetvli → M条vse32.v
```

目前dispatcher等待旧Ara工作排空，保持CPU请求直到QBS原子提交或异常返回。
engine完成全部计算后经commit等待实际final grant，才释放本条结果并回到IDLE。
所以直接加一个FIFO不会自动重叠下一命令；提前返回而又不跟踪结果及异常也不正确。

源码依据：

- 冻结 `inputs/llama/ggml/src/ggml-cpu/repack.cpp:4823`：准备和跨算子复用。
- 冻结 `inputs/llama/ggml/src/ggml-cpu/arch/riscv/qbs.cpp:1680`：按SDK调用建plan。
- 冻结 `inputs/ara/software/qbs/src/qbs_runtime.c:1133`：cursor与描述符/提交循环。
- 冻结 `inputs/ara/software/qbs/src/qbs_native_riscv.c:32`：native指令序列。
- 当前 `hardware/src/ara_dispatcher.sv:4980`及`hardware/src/vlsu/qbs/qbs_engine.sv:1091`：
  请求阻塞与最终提交。实施时还须对照板上RTL清单，不把当前HEAD自动当作板上版本。

冻结输入根目录为验证工作树的 `verification/out/fpga_unified_20261108_02/`。

## 3. 资源复用与新增范围

| 资源/逻辑 | 当前 | 合并候选 |
|---|---|---|
| 整数乘积槽 | 每周期32对 | 不变 |
| 外部读接口 | 128 bit | 不变 |
| FP32隐藏结果 | 128槽，共512 B | M1/N64使用64槽，不增加容量 |
| 权重双bank | 当前/下一R4 tile | 不变，不作为第二条独立命令的存储 |
| VRF出口/LDU | 原有最终提交接口 | 保留；M1结果跨两个寄存器 |
| 控制 | N≤32、M决定目的组 | 新增合并模式、N计数和索引映射、目的组校验 |
| 内存写接口 | native使用vse写最终输出 | 不新增硬件DMA写端 |

寄存器数组容量没有增加，不表示面积必然零增加：宽度、选择器、验证器、提交映射
和capability都会有控制成本。第一版禁止新建第二套结果数组、通用事务表或无界队列。

## 4. 执行和精确性契约

对每个K block，依次服务N64范围内的R4微块，然后推进K。每个输出仍按原来的
K block、subgroup及FP32累加顺序执行；只是交错独立输出，不改变模型权重、量化
格式、精度或累加顺序。权重数据和数学工作不减少。

合并命令在全部读取、计算成功后才提交N64；描述符/地址/读错误发生时，不能已经
向目的VRF写入前半块。这是新命令自身的原子性，不声称等价于两条旧指令的异常
提交边界。terminal必须等真实写回final acknowledgement，不能只等ready。

必须显式完成的设计工作：

1. **新模式编码及能力位。** 现有M1--M8与QBACC保留原编码；不能直接把旧`max_n`
   改为64，使旧SDK意外生成不支持的请求。编码通过ABI源和生成器定义。
2. **目的寄存器预留。** 在读取描述符之前就能知道需要两个对齐寄存器；M1不能再
   按旧的一寄存器规则接受、排相关和更新layout metadata。
3. **N、地址与index位宽。** 当前N≤32的验证、计数、结果索引、commit、stride和
   reference模型均逐项审核；不能只改一个localparam。尾块1..64使用明确byte enable。
4. **context生命周期。** 复用原generation、FILL/REUSE/RELEASE；DIRECT不能破坏
   其他已提交context。K过大或不满足能力时，保持现有DIRECT/fallback，不假定全驻留。
5. **可见异常状态。** 保持数值、fflags及固定RNE契约和原有vstart准入检查；
   不给原本独立于动态frm的QBS新增frm依赖。完整回归
   复位、fault drain和普通RVV前后交互。不删除原`ara_idle`安全门控。
6. **模型与SDK对齐。** 独立C参考、Spike/QEMU、RTL及native helper一致后，才接入
   GGML。新的M1/N64 helper使用两寄存器连续向量store，不把它误当作M2的两行结果。

## 5. 可量化机会与否决条件

当前Qwen3各Decode层的输出维度均可被64整除：Q/O=2048、K/V=1024、FFN gate/up
=6144、FFN down=2048，词表151936。因此每token的现有命令数可直接由形状推导：

```text
28 × (64+32+32+64+192+192+64) + 4748 = 22668 个 N32 命令
N64候选：11334 个命令；输出元素、权重字节、MAC数不变
```

这是命令数量预算，不是加速比。Prefill的大部分M4命令不在本候选范围，不能把
全部689916条命令都假设减半。完整模型的投影数据也包含准备和其他控制，不等于
可节省的命令边界时间。

在50 MHz下，要让本批4步Decode的33.2373485秒至少下降5%，每个原N32命令
平均需净省约916周期，即每个N64合并对约1833周期。该门槛包括全部新增控制、
提交及软件代价，不是只看descriptor或QBEXEC的局部周期。

仅描述符16 B的带宽不足以支撑方案；它远小于一个K2048/N32 tile的36,864 B
Q4_K或53,760 B Q6_K权重。真正待证实的是CPU/VRF往返及activation/replay等
边界成本。若经独立周期拆分发现这些成本达不到门槛，就否决“显著Decode收益”
目标，不靠扩大结果存储、取消fence或换弱基线挽救结论。

## 6. Prefill方向的前置筛选

M8已经存在，当前默认关闭。旧实验中它减少权重流量，却增加激活流量和串行装载；
理想供给下约慢6.1%，完整同工作区域还有11%--13%的退化例子。
不能将“打开WIDE_M”重新包装成新方案。参见 `qbs_adaptive_multirow_design.md` 和
`qbs_matrix_reuse_audit.md`。

M4全K驻留也不是只加一个入口：Q8_K的K2048需要9344 B，K6144需要28032 B，
均超过当前4672 B。固定K条带虽减少激活容量，却要求保存更多输出部分和。
下一设计须同时列出激活、权重和部分和三类容量及所有权，不能只列输入buffer。
此项暂不与M1合并一同实现，避免同时改变两个主要数据流而失去归因。

## 7. 最小验证顺序，而不是全模型盲跑

首先关闭测量工具缺口：Decode原时钟/记录扰动超过2%。独立的
`stage1_clock_preflight_20261109_01/clock-preflight`只测试Linux用户态rdtime可读性、
单调性及相对计时开销；不加载模型，不改用户计数器权限，不读设备寄存器，不重启。
非法CSR只在子进程触发，父进程给出失败状态。它读的是timebase，不是CPU cycles。

若可读且能与设备树timebase及CLOCK_MONOTONIC对账，后继probe才考虑采用这个
时钟；否则减少计时节点和ROI内元数据工作。不能将“能读”直接当作计时验收通过。
目前该小程序仅已静态交叉编译，未板测。

随后以完整K、真实权重的同一个N64输出区域，比较两条旧M1/N32与一条新M1/N64；
必须把fence/vset/descriptor/store及final drain一并计入。先做C/指令/局部检查，
再选一个真实SoC对照，不启动多套并行架构实验。首版包含Q4_K、Q6_K和一个不同
block几何的Q8_0，N尾、错误和普通RVV回归；机制若成立再覆盖其他profile和模型。

上述低扰动计时原本是规划关闭门槛。用户随后要求停止为规划追求精细证据，故按
最终计划将其保留为测量工具待办，不再阻塞阶段1。原2%验收并未改为PASS。
N64仍是可实施、可否决的后备候选，不是已取得收益或已验收的新硬件机制。
